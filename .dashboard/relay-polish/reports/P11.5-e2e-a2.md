## Failing Tests

### 1. REL-POL-A11Y-03: axe is clean with the @ mention menu open
**Status:** FAIL (consistent across 3 runs)
**Error:** Axe violation: `scrollable-region-focusable` (serious impact)
**Root cause (App Bug):** The mention menu's scrollable container (`.overflow-y-auto`) is not properly keyboard accessible. Although `tabindex={0}` was added to make it focusable, the violation persists. The element structure may need restructuring to properly expose the scrollable region to accessibility APIs.
**File:** `src/components/relay/MentionMenu.tsx` line 245-251
**Details:** Axe reports that the scrollable region must be in the tab order for users to access content that requires scrolling. The fix requires either:
- Using `role="region"` with proper aria-label
- Ensuring the scrollable element properly inherits focus semantics
- Potentially restructuring to use a listbox that properly handles overflow scrolling

### 2. REL-POL-A11Y-06: axe is clean with the shield popover in all three modes
**Status:** FAIL (consistent across 3 runs)
**Error:** Composer element fails to maintain focus after keyboard shortcut activation
**Root cause (App Bug):** After pressing the Relay keyboard shortcut to open the dock, explicitly calling `composer.focus()` does not actually set focus on the textarea. This suggests the composer may have a condition (disabled, aria-disabled, or other attribute) that prevents focus, or the keyboard shortcut doesn't properly initialize the relay state for focus.
**File:** `src/components/relay/RelayComposer.tsx` (presumed)
**Details:** The test structure is:
1. Reload page with permission mode set
2. Press keyboard shortcut to open relay dock
3. Explicitly focus the composer
4. Expect composer to be focused

Step 4 fails, indicating the composer is not accepting focus. This may be due to relay initialization state or disabled attribute application.

### 3. REL-POL-A11Y-08: axe is clean in dark mode at 320px panel width
**Status:** FAIL (consistent across 3 runs)
**Error:** Dock width cannot be resized to target 320px; stays at 384px
**Root cause (App Bug):** The relay dock has an apparent minimum width constraint of 384px. The `dragDockToWidth(page, 320)` function attempts to resize but the dock does not go below 384px.
**File:** Likely `src/components/relay/RelayDock.tsx` or its resize handler
**Details:** Expected width: ≤ 321px (320 + 1px tolerance)
Received width: 384px
The test scenario requires testing a11y at 320px width (narrow mobile panel), but the dock's minimum width prevents this. This is likely a legitimate app constraint, but the scenario description suggests 320px should be achievable.
